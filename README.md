# Fulcrum agent-s3

A Go agent for managing private S3 bucket services on **RustFS 1.0.4** through Fulcrum Core.

## Features

- One private bucket per service, with bucket-scoped credentials.
- Mandatory storage quotas, with increases supported.
- Customer-supplied secrets handled through the core's ephemeral vault properties.
- Credential rotation, suspension and resumption.
- Force deletion of objects, versions, delete markers and incomplete multipart uploads.
- Health checks and storage usage metrics.

**Development and isolated testing only.** The supplied deployment uses HTTP and
path-style S3 requests; do not expose it to the Internet.

## Deployment boundary

Customers must access the **S3-only gateway**, never the native RustFS endpoint.
The provider must keep administrative APIs and the console private; using different
URLs without network isolation is not sufficient. See [backend compatibility](docs/COMPATIBILITY.md).

The agent manages resources through APIs. It does not proxy object traffic or manage
containers, hosts or clusters. Run one active replica per `agentId`.

## Build

Tested with Go 1.27.0 on Linux amd64.

```sh
go build -trimpath -o bin/agent-s3 ./cmd/agent
docker build -t fulcrum-agent-s3:dev .
```

The container runs as `10001:10001` and has no shell.

## Configure Fulcrum

1. Register the [ServiceType](examples/service-type.json).
2. Add its ID to `serviceTypeIds` in the [AgentType](examples/agent-type.json), then register it.
3. Register the [metric types](examples/metric-types.json).
4. Create an agent for the provider with `configuration.rustfs`:
   - `endpoint`: private RustFS endpoint;
   - `clientEndpoint`: customer-facing S3 gateway;
   - `region`: S3 region;
   - `accessKey` and `secretKey`: administrative credentials, stored as persistent vault secrets.
5. Create an `agent` role token with `scopeId` set to the agent ID.
6. Supply the core URL and token locally, then start the agent.

See [.env.example](.env.example) for local settings. Never commit credentials; restrict
any local credential file to mode 0600.

```sh
export S3_AGENT_FULCRUM_API_URL=http://127.0.0.1:18000
# Supply S3_AGENT_FULCRUM_API_TOKEN through your secret-management mechanism.
./bin/agent-s3
```

Restart the agent after changing administrative credentials or timeouts.
Endpoints and region are immutable in the supplied schema: use a new agent for a
different backend. See [operations](docs/OPERATIONS.md) for configuration and recovery.

## Manage a service

Create a service with `POST /api/v1/services`, providing `agentId`, `serviceTypeId`,
`groupId`, `name` and these `properties`:

```json
{
  "quotaBytes": 1073741824,
  "secretAccessKey": "<strong random secret supplied by the customer>"
}
```

Bucket names and access key IDs are derived from the service ID. The customer keeps
the original secret; `agentInstanceData` returns only `endpoint`, `bucket`,
`accessKeyId`, `region` and `quotaBytes`.

Configure clients with the returned endpoint and region, SigV4 and `path` addressing.
Presigned URLs are generated by the S3 client.

| Operation | Core API |
| --- | --- |
| Increase quota or rotate the secret | `PATCH /api/v1/services/{id}`, using `properties` |
| Suspend access | `POST /api/v1/services/{id}/suspend` |
| Resume access | `POST /api/v1/services/{id}/resume` |
| Force delete | `DELETE /api/v1/services/{id}` |

**Deletion permanently removes service data.** It does not bypass retention or legal holds.
Operations are asynchronous: check the job result and service state, not just the HTTP response.

## Test

```sh
go test ./...
go test -race ./...
go vet ./...
```

Acceptance tests require local Docker with Compose, Python with venv, and a clean core
checkout at the revision in [tests/core-revision](tests/core-revision).

```sh
python3 -m venv .local/venv
.local/venv/bin/pip -q install -r tests/requirements.txt
CORE_DIR=../core bash scripts/prepare-e2e.sh
.local/venv/bin/python tests/backend_contract.py
.local/venv/bin/python tests/test_iam_boundaries.py
bash tests/network_boundary.sh
go build -race -o .local/agent ./cmd/agent
.local/venv/bin/python -u tests/e2e.py
```

The suite uses synthetic data and restarts its dedicated backend. Do not run two E2E
suites against the same fixtures. Generated credentials stay in ignored `.local/*.env`
files with mode 0600.

| Local endpoint | Purpose |
| --- | --- |
| `127.0.0.1:19080` | Customer S3 gateway |
| `127.0.0.1:19000` | Private RustFS access for the agent and trusted operators |
| `127.0.0.1:18000` | Test core |

[Verification results](docs/VERIFICATION.md) cover AWS CLI, boto3, quotas, multipart,
rotation, suspension and partial-deletion recovery.
[Operations](docs/OPERATIONS.md) documents fixture shutdown and known limitations.
